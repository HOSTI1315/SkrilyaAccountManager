запуска**: аккаунт стартует не в `RobloxPlayerBeta.exe` на Windows, а в **Roblox-клиенте внутри
Android-эмулятора** (LDPlayer / MuMu / MEmu), с логином по куке, заходом в конкретную игру и
отслеживанием состояния.

**Ничего изобретать не нужно.** Весь механизм уже написан, отлажен и отработал боем в другом проекте
пользователя — `c:\Users\User\Desktop\GameChecker` (Python). Задача этой сессии — **перенести

Соотношение с [V4-FEATURES-PLAN.md](V4-FEATURES-PLAN.md): тот документ — про перенос фич из RAM v4,

## 3. Архитектурное решение

**Порт механизмов на C# внутрь менеджера. Не тащить Python, не поднимать сайдкар-сервис.**

Почему так:
- Внешних зависимостей ноль: adb — обычный `.exe`, вызывается через `Process` ровно как сейчас
  вызывается `RobloxPlayerBeta.exe` в `Classes/ClientLauncher.cs`. Правило «не тащить новые тяжёлые
  зависимости» из V4-плана соблюдено.
- Куки у нас уже в руках (`Account.SecurityToken`, plaintext в памяти) — гонять их в сторонний
  процесс значило бы плодить копии секретов.
- Мониторинг, релаунч и бюджеты (`Classes/StuckDetector.cs`, `Relauncher.cs`, `LaunchBudget.cs`)
  уже написаны и абстрагированы от способа запуска — Android-запуск должен стать вторым источником
  вердиктов для них, а не параллельной вселенной.

Объём: ~600–800 строк C# на весь базовый функционал. Python-оригинал — 658 строк драйвера
плюс оркестратор, из которого нам нужна примерно треть.

**Альтернатива, если пользователь захочет массовость и трейд**: не портировать, а ходить HTTP в
уже готовую ноду GameChecker (`server.py`, `POST /gc/check`). Быстрее, но тогда менеджер не владеет
запуском и вся Android-часть живёт вне его. Решение — за пользователем, см. §11.

## 5. Механики по фазам

Каждая фаза самодостаточна и проверяема. **Не начинать фазу N+1, пока N не проверена руками.**

### Фаза 0. Ручное доказательство на одном инстансе

До единой строки C#. Цель — убедиться, что на этой машине эмулятор вообще пригоден.
Эталон последовательности: `tools/android_check_one.py`.

```powershell
# 1. adb ИМЕННО ОТ ЗАПУЩЕННОГО ЭМУЛЯТОРА (см. грабли, §9.1)
& "C:\...\LDPlayer\adb.exe" devices          # ждём state = device, не offline
& $adb -s emulator-5554 shell "su -c id"     # ждём uid=0
# 2. пакет Roblox-клиента
& $adb -s emulator-5554 shell "cmd package resolve-activity -a android.intent.action.VIEW -d roblox://placeId=1"
# 3. кукистор существует?
& $adb -s emulator-5554 shell "su -c 'ls -l /data/data/com.roblox.client/app_webview/Default/Cookies'"
# 4. схема таблицы (от неё зависит INSERT)
& $adb -s emulator-5554 shell "su -c 'sqlite3 /data/data/com.roblox.client/app_webview/Default/Cookies \".schema cookies\"'"
```

**Критерий прохода:** есть root, найден пакет, есть кукистор, `sqlite3` на устройстве отвечает.
Нет чего-то одного — дальше идти бессмысленно, чинить эмулятор (тумблер Root в настройках
LDPlayer/MuMu, один раз запустить Roblox руками до логин-экрана, чтобы создался кукистор).

### Фаза 1. `AdbClient` + обнаружение инстансов

Портировать: `adb_driver.py` стр. 73–520.

**`AdbClient`** — тонкая обёртка. Ключевое из оригинала:
- `rshell(cmd)` — выполнение под root **двумя способами**: `adb root` (MEmu-образы) либо `su -c '…'`
  (LDPlayer, production-build). `EnsureRoot()` проверяет **`su` первым**: на LDPlayer `adb root`
  роняет транспорт в offline, и обе последующие проверки видят пустоту → ложный вердикт «root нет».
- После `adb root` — реконнект **tcp-формы** транспорта (`emulator-5554` → `127.0.0.1:5555`),
  иначе устройство остаётся offline.
- `AppRunning()` — `pidof <pkg>` с фолбэком на `pgrep -f` (детект краша клиента).

**`EmulatorDiscovery`**:
- **adb брать из запущенного эмулятора**, а не из PATH: у каждого эмулятора свой adb, чужая версия
  показывает инстансы `offline`. Оригинал ищет по имени процесса (`dnplayer`, `mumunxmain`, `memu`,
  `nox`, `hd-player`) и берёт `adb.exe` рядом с exe процесса. В C# — `Process.GetProcesses()` +
  `MainModule.FileName` (или WMI, как в оригинале).
- LDPlayer: инстансы часто не регистрируются сами — `ldconsole.exe list2` даёт индексы,
  порт слота = `5555 + 2*index`, по каждому `adb connect 127.0.0.1:<port>`.
- **Дедуп транспортов**: один инстанс светится и как `emulator-5554`, и как `127.0.0.1:5555`.
  Без схлопывания по adb-порту на один инстанс поднимутся два воркера и подерутся за инъекцию куки.
- Повторять цикл обнаружения, **пока список растёт** (максимум 3 прохода): на ферме из 20+ инстансов
  adb-сервер «прилипает» не с первого раза.
- Авто-подъём (`ensure_ld_instances`): стартовать **пачками по 3 с паузой 5 с**, ждать загрузки до
  180 с. Холодный старт эмулятора упирается в CPU — все разом валят машину.

> ⚠ **Не перенаправлять stdout у `adb start-server` и `adb connect`.** Они порождают демон, который
> наследует пайп и держит его открытым — процесс-обёртка будет ждать EOF вечно, а таймаут убьёт
> только клиента. В C#: `RedirectStandardOutput = false` для этих двух команд (в оригинале — `DEVNULL`).

**Проверка фазы:** метод возвращает список серийников и путь к adb; в логе видно root-режим и пакет.

### Фаза 2. Вход по куке — `CookieInjector`

Портировать: `adb_driver.py` стр. 512–643. **Это самая ценная часть, здесь всё неочевидно.**

Механизм: нативный Android-клиент Roblox берёт личность из **Chromium-кукистора своего WebView** —
`/data/data/<pkg>/app_webview/Default/Cookies` (SQLite). Пишем туда `.ROBLOSECURITY` — клиент
стартует уже залогиненным. Ни тикета, ни пароля, ни UI-автоматизации.

Порядок строго такой:

1. **`am force-stop <pkg>` до записи.** Запись в живое приложение аккаунт не меняет: WebView держит
   сессию в памяти и перезапишет БД своим значением.
2. **Прогрев кукистора** для свежего клиента: если файла нет — `monkey -p <pkg> -c android.intent.category.LAUNCHER 1`,
   ждать появления файла до 45 с, снова force-stop. Схему создаёт сам WebView — подсовывать свою нельзя.
3. **Прочитать реальную схему**: `sqlite3 <db> '.schema cookies'`. Набор колонок **отличается между
   версиями Android** (A9 без `is_same_party`, A15 с ним). INSERT строится под фактические колонки,
   неизвестная колонка → `0`.
   Парсер схемы обязан резать по **запятым верхнего уровня** и брать тело `CREATE TABLE` по балансу
   скобок: табличное ограничение `UNIQUE (host_key, name, path)` ломает наивный split, куски `name` /
   `path)` утекают в список колонок и INSERT падает на `near ")"`. Это реально ловилось на Android 9.
4. **Значения**: `host_key='.roblox.com'`, `name='.ROBLOSECURITY'`, `path='/'`, `is_secure=1`,
   `is_httponly=1`, `is_persistent=1`, `has_expires=1`, `source_scheme=2`, `source_port=443`,
   `samesite=-1`, `encrypted_value=X''` (пусто — значение кладём открытым текстом в `value`).
   Времена — **Chromium-эпоха**: микросекунды с 1601-01-01, то есть `(unix + 11644473600) * 1e6`.
   `expires_utc` — +10 лет.
5. **`DELETE` + `INSERT`**, не `UPDATE`: строки может не быть вовсе.
6. Финальный `SELECT 'rows='||count(*)` — успех определяется по `rows=1` в выводе, а не по коду возврата.
7. **3 попытки** с повторным `force-stop` между ними: под нагрузкой adb-шелл отдаёт пустоту, а
   приложение успевает переоткрыться и залочить БД. Без ретрая одна осечка = потерянный аккаунт.
8. SQL заливать файлом через `push` в `/data/local/tmp/…` и `sqlite3 <db> < file 2>&1`, потом удалять.
   `2>&1` обязателен — иначе ошибка sqlite не видна и провал выглядит как успех.

Бэкап кукистора перед записью (`cp` под root → `pull`) — в оригинале есть, у нас пригодится для
диагностики; складывать в `%LOCALAPPDATA%\SkrilyaAccountManager\android-backups\`.

**Проверка фазы:** после инъекции и запуска клиент открывается уже под нужным аккаунтом
(скриншот `screencap` показывает домашний экран с ником).

### Фаза 3. Запуск в игру — `AndroidLauncher`

```
am start -n <pkg>/com.roblox.client.ActivityProtocolLaunch \
   -a android.intent.action.VIEW -d roblox://placeId=<placeId>
```

- **Компонент указывать явно** (`-n <pkg>/…`): на устройстве может стоять несколько Roblox-пакетов
  (официальный `com.roblox.client` и лайт-репаки вроде `free.noka9`), и без `-n` intent уйдёт не туда.
  Пакет определять через `cmd package resolve-activity` (кто ловит `roblox://`), с фолбэком на
  `pm list packages` по подстроке.
- **Заход к игроку** (наш аналог Follow): `roblox://placeId=<place>&userId=<uid>`. Обрабатывается
  лаунчером Roblox **до** Lua-скриптов, поэтому внутриигровые анти-скам-хуки его не глушат (в отличие
  от `TeleportToPlaceInstance`). URI обязательно в одинарных кавычках — `&` иначе уведёт команду в фон.
- **Смена игры на живом клиенте** — тот же deeplink, аккаунт не меняется (это телепорт).
  **Смена аккаунта** — только `force-stop` + инъекция + новый deeplink.

**Проверка фазы:** аккаунт из списка менеджера заходит в выбранную игру одной кнопкой.

### Фаза 4. Состояние — `LogcatWatcher`

Android-клиент Roblox пишет полный FLog в logcat: `adb -s <serial> logcat -d -s Roblox`.
Маркеры **те же, что в логе PC-клиента**, — то есть словарь состояний у нас уже есть.

Читать: `adb_driver.py` 47–70 (регулярки) и `android_orchestrator.py` 204–242 (классификация).

| Сигнал | Значение |
|---|---|
| `! Joining game '<jobid>' place <id>` | зашёл (`Joined`) — здесь же берём **jobId** |
| `Sending disconnect with reason: <N>` | дисконнект, `N` == Error Code из диалога |
| `264 / 273 / 276` | **аккаунт запущен с другого устройства** — вот ради чего `LaunchLock` |
| `268 / 272` | античит Roblox спалил executor — ретрай бесполезен |
| `280` | клиент устарел → обновить APK; прилетит на любом аккаунте |
| `267 / 291` | кик игрой/модерацией, часто анти-альт-гейт («don't have access … yet») |
| `600` | бан в этом плейсе |
| `524 / 533 / 773` | нет доступа (возраст/приватность/регион) |
| `generic-challenge-type=captcha`, `challengeDisplayed` | капча на `/join-game` — **проблема всей сессии**, а не одной игры |
| `pidof <pkg>` пуст | клиент упал (`app_crash`) |
| прочие коды | транзиент, ретраить |

Правила поведения, выстраданные там:
- **Краш не тратит попытку** — реджоин, но не более 15 раз подряд (страховка от битого инстанса).
- Капча по умолчанию **account-level**: висит на сессии, все последующие заходы упрутся в неё.
- Recovery между попытками: `hop` (телепорт в другую игру и обратно) → `reenter` (force-stop +
  повторная инъекция). Эскалация: первый ретрай — hop, дальше reenter.
- На провале — `screencap` в файл. Экономит часы диагностики.

Врезка: результат — `AndroidClientVerdict` того же вида, что `ClientVerdict` в `StuckDetector.cs`
(состояние, причина, возраст, аккаунт). Подписать `Relauncher` на него; `LaunchBudget` не менять —
кулдаун на аккаунт и потолок в час здесь применимы дословно.

**Проверка фазы:** в логе менеджера видно `Joined place … job …` для успеха и внятную причину
(`kicked`, `active_acc`, `captcha`) для провала.

### Фаза 5. In-game канал (опционально, но он у нас почти готов)

Если нужно не только «зашёл», но и «что происходит внутри» (жив ли персонаж, инвентарь, выполнить
скрипт) — нужен executor внутри эмулятора (Delta и аналоги) и скрипт в его autoexec.

**У нас для этого уже есть Nexus** — WS-сервер (`Nexus/AccountControl.cs`) с протоколом
«клиент подключается, менеджер шлёт команды». Порт `NexusPort`, сервис `/Nexus`,
клиент шлёт `?name=<username>&id=<userid>&jobId=<job>`. Ровно та же роль, что у `bridge_server.py`
в GameChecker. Портировать его WS-сервер **не нужно** — нужно научить Nexus работать с эмулятором:

1. **`AllowExternalConnections = true`.** Приложению внутри эмулятора loopback хоста недоступен —
   только LAN-IP. Внешним клиентам обязателен `&token=<NexusToken>` (уже реализовано).
2. **LAN-IP определять правильно.** `provision.py:detect_lan_ip` — под VPN исходящий интерфейс это
   VPN-адрес (`198.18.x` — benchmarking-диапазон, его подсовывают FlClashX и подобные), и скрипт
   уедет в никуда. Брать приватный адрес, предпочитая `192.168.*`, затем `10.*`, `172.*`,
   пропуская link-local и `198.18/19`.
   Для QEMU-NAT образов (классический AVD, MEmu) альтернатива — хост виден как `10.0.2.2`.
3. **`adb reverse` для этого не годится.** HTTP-стек Roblox не видит reverse-loopback приложения —
   проверено. Только LAN-IP или `10.0.2.2`.
4. **Провижининг скрипта** (`provision.py:provision_device`): `install -r -g` для APK
   (split-APK → `install-multiple`), `mkdir -p /sdcard/<Executor>/Autoexecute`, push скрипта.
   **Проверять содержимое файла на устройстве, а не факт его наличия**: `su -c cp` молча падает на
   части инстансов, а `ls` показывает старый файл как «ок» — из-за этого инстансы месяцами держали
   неверный IP/порт. Схема деплоя: прямой `push` → если файл пуст, `push` в `/data/local/tmp` +
   `su -c cp` → затем `cat` и сверка подставленных значений.
5. **Телепорт убивает скрипт**, а autoexec при телепорте (в отличие от холодного старта) не
   срабатывает — в `gc_client.lua` это решено через `queue_on_teleport` (скрипт переисполняет себя в
   новом сервере). Если наш скрипт должен переживать телепорты — перенести этот приём.

> Delta должна быть **разблокирована** (введён ключ), иначе autoexec молча не исполняется и это
> выглядит как «скрипт не работает». Первая гипотеза при тишине канала — всегда эта.

### Фаза 6. Массовость: пул, UI, мост

Нужно, только если запускать больше одного аккаунта разом.

- **`AndroidPool`**: слот = инстанс. Аренда под аккаунт, возврат сразу после (`instance_pool.py`).
  Лимит одновременных — настройка, дефолт по свободной RAM (≈1.1 ГБ на слот).
- **Уникальность кук в пачке обязательна**: один аккаунт на двух инстансах = Error 276, обе сессии
  портятся. В `run_task` это `dict.fromkeys` перед стартом; у нас — проверка перед постановкой в очередь.
- **Вотчдог** (`ld_watchdog.py`): инстанс, переставший отвечать на `adb shell echo`, помечается
  мёртвым, аккаунт возвращается в очередь (до 3 раз), инстанс перезапускается через `ldconsole`.
  Без этого смерть инстанса выглядит как «аккаунт не прошёл».
- **UI**: экран «Эмуляторы» — список инстансов (серийник, статус, root, пакет, кто на нём сейчас),
  кнопки «Обнаружить», «Провижинить», «Запустить выбранные аккаунты». Регистрация в
  `Screens.destinations` (`ui/app.js:1382`), разметка в `ui/index.html`, шаблоны — в `<body>`,
  не внутри перерисовываемых контейнеров (грабля из раздела L V4-плана).
- **Пауза между запусками** считается **на точку выхода**, а не глобально — то же решение, что
  принято для PC-лаунчера (раздел M V4-плана). Для эмуляторов точка выхода — сам инстанс.

## 6. Настройки (`RAMSettings.ini`, новая секция `[Android]`)

Дефолты задавать там же, где остальные (`AccountManager.cs`, блок `if (!General.Exists(...))`).
Всё новое — **opt-in, по умолчанию выключено**.

| Ключ | Дефолт | Смысл |
|---|---|---|
| `EnableAndroid` | `false` | главный тумблер |
| `AdbPath` | пусто | пусто = авто-детект от запущенного эмулятора |
| `Serials` | пусто | пусто = все обнаруженные |
| `Package` | пусто | пусто = авто-детект (`com.roblox.client` / репак) |
| `MaxInstances` | `2` | потолок одновременных |
| `AutoStartInstances` | `false` | поднимать инстансы через `ldconsole` |
| `LaunchBatch` / `LaunchDelay` | `3` / `5` | пачки холодного старта |
| `ConnectTimeout` | `90` | сек ожидания захода |
| `AutoexecPath` | `/sdcard/Delta/Autoexecute` | папка autoexec executor'а |
| `LanIp` | пусто | пусто = автодетект (см. фаза 5, п. 2) |
| `BackupCookieStore` | `true` | бэкап кукистора перед инъекцией |

## 7. Порядок работ

1. **Фаза 0** — ручная проверка эмулятора (полчаса, без кода).
2. **Фазы 1–3** — минимально полезный результат: «выбрал аккаунт → он в игре на эмуляторе».
   Это и есть то, что просил пользователь.
3. **Фаза 4** — состояние и релаунч.
4. **Фаза 5** — только если нужен in-game контроль.
5. **Фаза 6** — только если нужна массовость.

## 8. Контракты моста (фаза 6)

Регистрация как у всех остальных, в `Classes/Bridge/BridgeApi.cs`
(шаблон — `UiBridge.Register`, `Classes/Bridge/UiBridge.cs:53`):

```
android.devices    -> [{ serial, state, root, package, busyAccount, androidVersion }]
android.discover   -> то же, но с принудительным пересканом
android.provision  { serials[] } -> [{ serial, apk, autoexec, ip, ok, error }]
android.launch     { account, placeId, serial?, jobId? } -> { serial, state, jobId }
android.stop       { serial } -> ok
android.state      { serial } -> { state, reason, account, ageSeconds }
android.screenshot { serial } -> dataUri            // диагностика, дешёвая и полезная
```

События (push в страницу): `android.state` при смене вердикта, `android.progress` для пачки —
по образцу `launch.progress` / `freeitems.progress`.

**Куки через мост не ходят** — то же правило, что для учётных данных прокси (раздел L V4-плана).
Страница передаёт имя аккаунта, куку достаёт приложение.

## 9. Грабли (за каждую заплачено временем)

1. **Чужой adb → все инстансы `offline`.** Версии adbd у LDPlayer/MuMu/scrcpy разные. Брать adb
   рядом с exe запущенного эмулятора.
2. **Пайп на `adb start-server`/`connect` вешает вызов навсегда** — демон наследует stdout.
3. **Один инстанс = два транспорта** (`emulator-5554` и `127.0.0.1:5555`). Не схлопнув, получите два
   воркера на один инстанс.
4. **`adb root` на LDPlayer роняет транспорт в offline** — проверять `su` первым.
5. **Инъекция в живое приложение бесполезна** — только после `force-stop`.
6. **Схема таблицы `cookies` разная по версиям Android** — строить INSERT по фактическим колонкам.
7. **Табличные ограничения ломают наивный парсер схемы** — резать по запятым верхнего уровня.
8. **БД лочится** — ретраи с повторным force-stop.
9. **Свежий клиент не имеет кукистора** — прогреть запуском.
10. **`su -c cp` молча падает** — сверять содержимое файла, а не наличие.
11. **`adb reverse` не работает для HTTP из Roblox** — только LAN-IP / `10.0.2.2`.
12. **LAN-IP под VPN определяется неверно** (`198.18.x`) — фильтровать.
13. **Один аккаунт на двух устройствах = Error 276** — уникальность кук + `LaunchLock`.
14. **Телепорт не запускает autoexec** — скрипт должен ставить себя в очередь на переисполнение.
15. **Delta без ключа = тишина в канале**, а не ошибка.
16. **Холодный старт пачкой убивает CPU** — по 3 с паузой.
17. **`ldconsole list2` врёт про `running`** на части сборок — факт запуска определять через adb.
18. **RAM ~1.1 ГБ на инстанс** — это и есть потолок фермы, а не CPU.

## 10. Чего не делать

- **Не тащить в менеджер чекер/трейд/ридеры/прайсинг из GameChecker.** Это отдельный продукт;
  сюда переносится только «залогинься и зайди в игру».
- **Не хранить куки на устройстве дольше сессии.** Инъекция — это запись секрета в файл на
  эмуляторе; после работы аккаунта затирать строку `.ROBLOSECURITY` (`DELETE`) при смене слота.
- **Не переименовывать `AccountData.json` / `RAMSettings.ini` / `RAMTheme.ini`** и не трогать
  `Cryptography.RAMHeader` (правило из V4-плана).
- **Не делать Android-запуск обязательным путём.** PC-лаунчер остаётся дефолтом, Android — второй
  вариант по явному выбору.
- **Не автоматизировать UI эмулятора кликами** (`input tap` по координатам). Всё делается deeplink'ами
  и adb-командами; координатная автоматизация ломается от версии к версии.
- **Не поднимать Python-сайдкар** без явного решения пользователя (см. §11).

## 11. Открытые вопросы к пользователю

Задать **до** начала фазы 1 — ответы меняют объём работ:

1. **Какой эмулятор целевой?** LDPlayer (в GameChecker он основной, `ldconsole` поддержан), MuMu
   (порты 16384+), MEmu (adb-root вместо su). От этого зависит модуль обнаружения.
2. **Нужен ли executor внутри эмулятора** (фаза 5), или достаточно «зашёл в игру и держится»?
   Executor = плюс Delta/APK-провижининг и ключи.
3. **Массовость**: один-два аккаунта руками или ферма на 8–10 слотов? Второе включает фазу 6 целиком.
4. **Порт или сайдкар**: если Android-часть нужна «вчера и массово», дешевле ходить HTTP в готовую
   ноду GameChecker, чем портировать (см. §3).

## 12. Как проверять

Сборка — как обычно:

```powershell
cd "c:\Users\User\Desktop\Roblox-Account-Manager-master"
dotnet build "RBX Alt Manager\RBX Alt Manager.csproj" -c Debug
```

Предостережения по smoke-тестам действуют полностью (раздел 3 V4-плана): у пользователя постоянно
запущен стоковый RAM и живые `RobloxPlayerBeta` — не запускать тест из `%TEMP%`, не включать
`EnableMultiRbx`, убивать тестовый процесс.

Дополнительно для Android:
- Проверять на **одном** инстансе, пока фазы 1–4 не зелёные.
- `screencap` — главный инструмент диагностики: непонятное состояние всегда видно на скриншоте.
- Ферма пользователя может быть занята другой работой — перед подъёмом инстансов проверять
  `adb devices` и не трогать чужие.
